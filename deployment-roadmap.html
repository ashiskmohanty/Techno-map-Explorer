Deployment Roadmap

A pragmatic path from a single-instance, file-backed application to a secure, reusable and horizontally scalable SaaS platform for teams that upload the same supported Excel inputs.

Target: multi-tenant SaaSRuntime: Azure Container AppsData: PostgreSQL + Blob StorageJobs: Service Bus + workersDelivery: IaC + CI/CD

Move state first, scale second

The code already runs in a container, but the application directory is also its database, document store, audit log and backup system. Multiple replicas cannot safely share that model. The first architectural goal is therefore a stateless web container with every mutable item stored in a tenant-aware Azure service.

1

Reusable application

One product deployment serves many teams. Tenant context determines data, configuration, limits and SAP connection settings.

2

Two storage classes

Blob Storage holds large files; PostgreSQL holds searchable, relational and transactional application records.

3

Asynchronous rebuilds

Excel processing leaves the HTTP request path and runs as a durable queued job with progress, retries and audit history.

◆
Recommended product boundary

Launch the SaaS first around customer-supplied Excel files. Treat direct SAP RFC/ADT connectivity as a later enterprise connector because customer SAP systems normally sit behind private networks and require tenant-specific credentials, firewall rules and SDK licensing.

Non-negotiable launch gates

  • Every request resolves an authenticated tenant and user
  • No mutable data is written inside the container
  • Uploads are validated, size-limited and malware-scanned
  • Database and blob queries are tenant-scoped by design
  • Rebuild jobs are idempotent and retry-safe
  • Secrets use managed identity and Key Vault
  • Backups have a tested restore procedure
  • Per-tenant quotas and usage metering are enforced

Target Azure architecture

The request path stays lightweight. Uploads go directly to Blob Storage, metadata goes to PostgreSQL, and long-running rebuilds are queued. The web tier can then add or remove replicas without changing application state.

Interactive request path

Authenticate user → resolve tenant → authorize role → query PostgreSQL/cache → return tenant-filtered data. It should not parse workbooks, create ZIPs or wait for SAP.

Background job path

Issue direct-to-Blob upload → create job record → publish message → worker validates and rebuilds → commit new dataset version → notify UI through polling or push.

Network path

Use private endpoints for PostgreSQL, Storage, Key Vault and AI services. Give Container Apps controlled outbound traffic through a NAT Gateway when customers require IP allowlisting.

SAP connectivity path

For private SAP systems, use VPN/ExpressRoute or a customer-hosted connector that pushes approved extracts. Store each tenant's secret references in Key Vault, never in the shared database.

!
Do not mount one shared file system and call it scale

Azure Files can provide a low-change bridge for a pilot, but process-level file locks, append-only JSONL and whole-file rewrites remain contention and corruption risks. It is a migration bridge, not the SaaS end state.

Repository changes required

Introduce storage interfaces

Create repository abstractions such as ObjectRepository, FeedbackRepository, BlobRepository and JobRepository. Keep local-file implementations for development and add Azure implementations behind configuration.

Add tenant context middleware

Validate the Entra token, resolve tenant_id, user_id and roles once, and pass that context to every repository and audit call.

Version datasets

Every successful rebuild creates an immutable dataset version. Switch the tenant's active version in one database transaction; never partially overwrite the live catalogue.

Split web and worker images

Use the same source image with separate commands. Web serves Flask; worker consumes jobs and runs build_data.py against Blob inputs and database output.

Make all operations idempotent

Assign job IDs, content hashes and version IDs. Replayed Service Bus messages must detect completed work rather than duplicate records.

File-to-Azure data migration

Do not put every JSON document into one database column. Choose storage by access pattern: blobs for large immutable content, relational tables for records that must be filtered or updated, and telemetry services for operational events.

Migration runbook

Inventory and freeze schemas

Document each JSON shape and workbook schema. Add schema versions and validation tests before moving data.

Create tenant and dataset tables

Make tenant_id mandatory on all tenant-owned tables. Add composite indexes beginning with tenant_id.

Build one-time importers

Import current files as the first tenant and first dataset version. Reconcile counts, dependency edges, mappings and hashes against the existing application.

Dual-read during verification

In a non-production environment, compare file-backed and Azure-backed API responses for representative searches, process tiles and object details.

Cut over writes

Stop file writes, take a final snapshot, import deltas, switch repository configuration, run smoke tests and keep a documented rollback window.

Retire file state

After reconciliation and restore testing, remove writable local volume assumptions. Keep local repositories only for developer mode and automated tests.

Design tenant isolation before onboarding team two

A tenant represents a customer team or organization. Identity, data, jobs, files, secrets, quotas and audit records must all resolve through the same immutable tenant identifier.

Shared application

All tenants use the same Container App and code revision. This keeps delivery simple and efficient.

Recommended default

Shared database, isolated rows

All tenant-owned tables include tenant_id. Enforce filters in repositories and PostgreSQL row-level security as defense in depth.

SMB / team tier

Deployment stamps

Large or regulated customers receive a dedicated database/storage stamp while the control plane routes them to the right stamp.

Authorization flow

Authenticate

Validate Microsoft Entra issuer, audience, signature, expiry and subject. Do not trust a tenant ID supplied only in a URL or request body.

Resolve membership

Map the authenticated subject to an active SaaS membership and tenant. For users in several teams, require an explicit tenant switch.

Authorize capability

Use roles such as Tenant Admin, Data Manager, Analyst and Viewer. Keep platform operations separate from tenant administration.

Constrain data access

Repository methods require tenant context; Blob paths start with tenant ID; Service Bus messages contain signed/internal tenant context; database RLS blocks cross-tenant rows.

Audit

Record actor, tenant, action, target, outcome, correlation ID and timestamp for uploads, rebuilds, restores, role changes, exports and SAP access.

!
Backups are also tenant data

The current full-application ZIP is useful for a single installation. In SaaS, provide tenant-scoped export/restore and platform-level disaster recovery separately. A tenant administrator must never list or restore another tenant's snapshot.

Scale on measured bottlenecks

Horizontal web scaling becomes safe after state is externalized. Worker scaling, database tuning and regional expansion should then follow real queue, latency, storage and tenancy signals.

Pilot
1–5 teams

Topology

One region, one Container App, one worker, PostgreSQL, Blob Storage and Service Bus. Minimum one web replica.

Focus

Tenant isolation, schema validation, restore drills, cost telemetry and product usage.

Growth
5–50 teams

Topology

Minimum two web replicas, HTTP autoscaling, queue-based worker autoscaling, database HA, Front Door/WAF and Azure Managed Redis if measured caching need exists.

Focus

p95 latency, noisy-neighbor quotas, connection pooling, job concurrency, dead-letter handling and support runbooks.

Enterprise
50+ teams

Topology

Regional deployment stamps, tenant routing, dedicated stamps for regulated customers, AI Search partitions and read replicas where justified.

Focus

Data residency, capacity automation, regional failover, contractual RTO/RPO and per-tenant cost allocation.

Container Apps scaling

Scale the web tier on concurrent HTTP requests. Set minimum replicas to 2 for production availability and maximum replicas from a tested PostgreSQL connection budget.

Worker scaling

Scale on Service Bus queue length/age. Cap total and per-tenant concurrency because workbook parsing is memory-heavy and one customer must not consume all workers.

Database scaling

Use connection pooling, bounded application pools, tenant-leading indexes and pagination. Archive old dataset versions according to policy before increasing compute.

Blob scaling

Upload directly with short-lived scoped URLs, use lifecycle rules for cool/archive tiers, and avoid proxying large files through Flask replicas.

  • Application Insights distributed tracing
  • Correlation ID from request through worker
  • Health, readiness and dependency probes
  • Service Bus dead-letter alerts and replay tooling
  • PostgreSQL slow-query and connection alerts
  • Blob capacity and failed operation alerts

  • Quarterly restore and failover exercises
  • Documented incident and tenant-notification runbooks

Phased delivery roadmap

Time ranges are planning estimates for a small product team and should be recalibrated after a technical spike. Each phase has an exit condition; avoid adding AI sophistication before tenancy and data correctness are proven.

Phase 0
Product decisions

Define the SaaS contract

  • Choose tenant definition, target customer, regions and data residency.
  • Define supported workbook schemas, maximum sizes and rebuild SLA.
  • Define roles, retention, export/deletion, plans and usage limits.
  • Choose input-files-only MVP versus direct SAP connectivity.
1–2 weeks
Exit: approved product and threat model
Phase 1
Cloud foundation

Deploy the current app safely

  • Create dev/test/prod subscriptions or resource groups and infrastructure as code.
  • Build image in Azure Container Registry; deploy Container Apps with managed identity.
  • Add Key Vault, Application Insights, Log Analytics and CI/CD using workload identity federation.
  • Use temporary persistent storage only for migration testing, not as the final SaaS model.
2–3 weeks
Exit: repeatable non-production deployment
Phase 2
Externalize state

Replace mutable local files

  • Add repository interfaces and PostgreSQL schema.
  • Move source workbooks, exports and backup artifacts to private Blob Storage.
  • Migrate corrections, edits, mappings, feedback, jobs and audits to PostgreSQL.
  • Import the current installation and reconcile every object count.
4–6 weeks
Exit: container filesystem is read-only/ephemeral
Phase 3
Multi-tenancy

Onboard teams securely

  • Add Entra authentication, tenant membership and application roles.
  • Enforce tenant context in database, Blob paths, jobs, logs and exports.
  • Create tenant admin onboarding, quota and retention workflows.
  • Run automated cross-tenant isolation and authorization tests.
4–6 weeks
Exit: independent test tenants pass isolation tests
Phase 4
Async rebuild

Separate ingestion from web traffic

  • Add direct Blob uploads, job records, Service Bus and worker process.
  • Add workbook malware scanning, schema validation, content hashes and idempotency.
  • Publish immutable dataset versions and atomically activate successful versions.
  • Add progress, retry, cancel and dead-letter administration.
3–5 weeks
Exit: rebuild survives web restarts and message replay
Phase 5
Production hardening

Prove reliability and security

  • Add Front Door/WAF, private endpoints, network controls and Defender scanning.
  • Load-test realistic tenants, uploads and concurrent rebuilds.
  • Test PostgreSQL PITR, Blob recovery, tenant export and disaster runbooks.
  • Add SLO dashboards, alerts, budgets, support procedures and privacy controls.
3–4 weeks
Exit: launch checklist and restore drill approved
Phase 6
Scale & intelligence

Add only measured capabilities

  • Introduce Azure Managed Redis when repeated query load justifies it.
  • Add Azure AI Search for semantic/hybrid retrieval over large catalogues.
  • Add deployment stamps for regional residency or dedicated enterprise isolation.
  • Build metering, subscriptions, billing integration and customer-facing usage views.
Continuous
Exit: driven by usage and contracts
◆
Practical first release

For the fastest responsible SaaS MVP, complete Phases 0–4 for uploaded workbooks, run in one Azure region, and defer live SAP connectivity, multi-region active/active, AI Search and billing automation. Those features add material complexity but are not required to prove reusable team value.

Before production approval

  • Infrastructure recreated from code in a clean environment
  • No secrets in source, image, logs or client storage
  • Two test tenants cannot access each other's rows or blobs
  • Rebuild replay produces one correct dataset version
  • Failed rebuild never replaces the active dataset
  • Database and Blob restore tested within target RTO
  • Scale test validates DB connection budget
  • Large uploads bypass the Flask request body
  • Usage limits prevent noisy-neighbor exhaustion
  • Tenant deletion/export workflow is tested
  • Operational dashboards and paging routes are owned
  • Cost budgets and service ownership are documented
